# 0002: JSON on the Mac side

- Status: accepted
- Date: 2026-10-31

## Context

The native client must read AppView and PDS responses: timelines, profiles,
threads, notification lists, DID documents and session replies. The bridge used
TypeScript objects; the Mac has a small, fixed stack and no C99 runtime
guarantees.

Wolfram's JSON is cJSON, which is C99 and allocates. The existing Mac client
already carries `macos9/json_min.c`: a bounded, allocation-free C89 scanner that
validates a document, walks objects and arrays with two pointers, and reads
strings, integers and booleans. It was written for the bridge protocol and is
covered by `test_json_min`.

## Decision

Reuse `json_min` for the native AT Protocol client. Do not add cJSON or another
JSON library to the Mac target.

Responses are read in place from the buffer Wolfram returns and freed with
`wf_response_free`; the scanner does not copy strings except into caller-owned
bounded fields. Display text is truncated by capacity, identifiers (DID, token,
URI) fail closed when they do not fit.

## Alternatives considered

- **cJSON (MIT).** Rejected: C99, heap allocation per node, and it would add a
  library to a target whose whole transport is deliberately small.
- **Wolfram's JSON.** Rejected for the same C99/heap reason; Wolfram's own Mac
  OS 9 target avoids it (`json_min.h` documents this).
- **A tree parser written for this change.** Rejected: the existing scanner
  already covers the access patterns, and a second parser is a second set of
  bugs.

## Consequences

- The scanner is not a general JSON library. Callers navigate to a member and
  read it; there is no path expression and no mutation.
- Arrays of bare strings (such as `alsoKnownAs`) are not read yet. The phase 1
  code does not need them; adding an accessor is cheaper than a tree.
- Deep nesting is bounded by `PLATINUM_JSON_MAX_DEPTH`, so a hostile body cannot
  exhaust the stack.
