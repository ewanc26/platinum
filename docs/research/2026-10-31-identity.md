## Findings

- A handle resolves to a DID by **either** a DNS TXT record at
  `_atproto.<handle>` **or** an HTTPS document at
  `https://<handle>/.well-known/atproto-did` whose body is the DID. The spec
  treats the HTTPS method as first-class, not as a fallback for a proprietary
  endpoint.
- `com.atproto.identity.resolveHandle` is a PDS/AppView convenience. It returns
  `{"did":"..."}`. It is not the only handle method and it requires a service
  base before the account's PDS is known.
- DID documents are fetched from the PLC directory (`https://plc.directory/<did>`)
  for `did:plc`, or from the host in a `did:web` with the method's port/path
  rules. The `#atproto_pds` service's endpoint is the PDS.
- The DID spec requires bidirectional validation: resolve handle -> DID, fetch
  the DID document, and check its `alsoKnownAs` (`at://handle`) matches the
  handle. A document that merely claims a handle is not proof.
- Live check: `https://plc.directory/did:plc:z72i7hdynmk6r22z27h6tvur` returned
  `alsoKnownAs: ["at://bsky.app"]` and
  `serviceEndpoint: "https://puffball.us-east.host.bsky.network"`.

## Not verified

- Whether `did:web` is used by any PDS a Platinum user is likely to sign in to.
  The parser supports it; it is not exercised against a live account.
- DNS TXT resolution. Open Transport can do DNS, but the spec's HTTPS method is
  enough for a client and avoids a second resolver path. Not implemented.

## ADR impact

- ADR 0003 is revised: the HTTPS `.well-known` method is the primary handle
  resolution, with `resolveHandle` as a fallback. New ADR 0008 records this.
- A bidirectional handle/DID check is still missing from `atproto_identity.c`;
  the parser needs a bare-string-array accessor in `json_min` or a small
  dedicated reader.
