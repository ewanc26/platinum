# Secure storage of the refresh token

Date: 2026-10-31.

## Sources

- https://leopard-adc.pepas.com/documentation/Carbon/Reference/Keychain_Manager/Reference/reference.html
  (Apple Carbon Keychain Manager reference mirror; search snippet, page timed
  out on direct fetch)
- https://en.wikipedia.org/wiki/Keychain_(software) (introduced with Mac OS 8.6)
- Apple CarbonLib availability note in the Keychain Manager reference:
  "Available in CarbonLib 1.1 and later when KeychainLib 1.0 or later is
  present. Available in Mac OS ..." (snippet truncated)
- Local Platinum `macos9/prefs_file.c`, `macos9/config.c` (plain text
  Preferences file; no encryption)

## Findings

- ADR 0004's premise "Mac OS 9 has no Keychain" is **false**. Keychain shipped
  from Mac OS 8.6, and the Carbon Keychain Manager (`KCAddGenericPassword`,
  `KCFindGenericPassword`, `KCDeleteItem`) is documented as available in
  CarbonLib 1.1+ when KeychainLib is present. Mac OS 9.2.2 has both.
- A generic-password keychain item can hold arbitrary bytes, so a refresh JWT
  fits. The login keychain is normally unlocked at login, which makes this a
  practical store for a GUI app.
- Whether Retro68's Multiversal Interfaces ship `Keychain.h`, and whether the
  current CMake application links CarbonLib/KeychainLib, is **unverified**.
  There is no Keychain header in Platinum's `retro68-includes/` and no local
  Retro68 install to inspect.
- Preferences files are plain text, creator/type are not protection, and any
  process with file access can read them. Persisting a refresh token there is
  not acceptable while a Keychain path exists.

## Decision

- Supersede ADR 0004 with ADR 0007: use the Carbon Keychain Manager for the
  refresh token; keep the access token and password in memory only; do not
  write any token to a Preferences file.
- Do not implement a plaintext Preferences fallback "for compatibility". If
  Keychain is unavailable at runtime, keep the session in memory and require
  sign-in again at launch; report the condition.
- The session layer exposes persistence as a callback so host tests can use a
  fake store and the Mac implementation can be swapped without changing the
  protocol code.

## Not verified

- Keychain header presence under Retro68; exact link library; whether a generic
  password item prompts on first use on OS 9.2.2.
- Keychain access from a 68k build. macTLS is PowerPC-only, so 68k networking
  is already unavailable; Keychain storage is PowerPC-only in practice.
